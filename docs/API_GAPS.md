# API GAPS — Lo que el frontend necesita y la API no ofrece

Registro de lo que la tienda pública necesita de la API base-shop y que su contrato (`docs/api/API_SPEC.md`, versión 1.8.0) no cubre o cubre a medias. Cada brecha se comunica al usuario y se resuelve en base-shop con su propio flujo; el frontend no la simula (`AI_WORKFLOW.md`, "Cambios que tocan la API").

## Estados

- ABIERTA: detectada y comunicada, sin decisión.
- DECIDIDA: hay decisión (en la API o en el frontend) y falta implementarla.
- RESUELTA: la API publicó el cambio y `docs/api/` ya está sincronizada, o se decidió que no hace falta.

## Brechas

| ID | Brecha | Impacto en la tienda | Propuesta | Prioridad | Estado |
|---|---|---|---|---|---|
| G-01 | **Aviso de privacidad sin dueño en la API.** El registro (`POST /v1/auth/register`) y el checkout de invitado (`POST /v1/orders`) exigen `privacyNoticeVersion`, pero la API acepta cualquier texto de 1 a 50 caracteres: no publica el texto del aviso ni cuál es su versión vigente, y no comprueba la versión recibida (base-shop ADR-0067). Solo publica los plazos de conservación (`GET /v1/privacy/retention-policy`) | La tienda tiene que mostrar el aviso y enviar su versión. Si cada cliente inventa la versión, la constancia legal de qué aceptó el comprador queda en manos del frontend | (a) La API publica el aviso vigente (texto o URL y versión) y rechaza versiones que no existen; o (b) el frontend es el dueño del texto y de la versión, con un ADR-F que lo diga. Requiere revisión legal (base-shop `PROJECT.md` §9) | Alta: bloquea registro y checkout de invitado | ABIERTA. Mientras tanto, la versión sale de `NUXT_PUBLIC_PRIVACY_NOTICE_VERSION`, la misma variable y valor que usa el backoffice (su G-19, ADR-F010) |
| G-02 | **Imágenes solo en tamaño original.** La API guarda y sirve cada imagen tal como se subió, hasta 5 MB, sin miniaturas ni tamaños derivados, y sin quitar metadatos EXIF (base-shop ADR-0024, ADR-0121) | El listado del catálogo descargaría imágenes completas por cada tarjeta: lento en teléfonos y costoso en datos | (a) La API genera tamaños derivados (miniatura, tarjeta, detalle) al subir; o (b) un CDN que redimensione, al decidir el hosting (PF-09). Como la tienda es una SPA estática (ADR-F005), no tiene un optimizador de imágenes propio: en local se usan las originales con carga diferida, y (a) o (b) hacen falta antes de producción | Media | ABIERTA |
| G-03 | **Métodos de pago no consultables públicamente.** Hoy solo existe el pago manual en tienda, y solo si un superadministrador lo habilitó (base-shop ADR-0162). La configuración (`GET /v1/admin/payment-settings`) es solo para el staff; un cliente que intenta pagar con el pago manual apagado recibe 400 `validation-error` | La tienda no puede saber antes del checkout si hay forma de pagar. El comprador podría colocar la orden, apartar stock y descubrir después que no puede pagarla | Ruta pública de solo lectura con los proveedores habilitados (por ejemplo, `GET /v1/payments/providers`). El backoffice ya consulta la configuración con permisos de staff (su G-02); falta la lectura pública | Alta: afecta al checkout | ABIERTA |
| G-04 | **Sin pago en línea.** El único pago real es en la tienda física (`action.type: PAY_IN_STORE`); PayPal está semiimplementado y fuera del MVP, y Mercado Pago y Stripe están pospuestos (base-shop ADR-0040, ADR-0158, T-191 a T-193) | La compra en línea termina con instrucciones para pagar en la tienda. Es suficiente para el entorno local, no para vender en línea | Decisión de negocio: con qué proveedor cobrar antes de abrir la tienda. El frontend se diseña con `action.type` extensible (`REDIRECT` llegará con PayPal) | Media: no bloquea el desarrollo local | ABIERTA |
| G-05 | **Datos del envío no públicos.** El costo fijo, el monto para envío gratis y el plazo de entrega estimado solo los ve el staff (`GET /v1/admin/shipping/method`). El cliente ve el costo hasta cotizar el checkout (`CheckoutQuote`) | La tienda no puede mostrar "Envío gratis desde $1,500" ni el plazo estimado en el producto o el carrito sin escribir esos valores en el código, que dejarían de coincidir cuando el administrador los cambie | Ruta pública de solo lectura con `flatFee`, `freeShippingThreshold` y el plazo (por ejemplo, `GET /v1/shipping/method`) | Baja | ABIERTA |
| G-06 | **Datos de la tienda no públicos.** Nombre, dirección y teléfono de la tienda existen como configuración de la API, pero solo el staff los consulta (`GET /v1/admin/store-profile`, base-shop ADR-0163) | El pie de página, el contacto y las instrucciones de pago en tienda ("dónde pagar") necesitan la dirección de la tienda física | Ruta pública con los datos que la tienda quiere mostrar; o configuración propia del frontend, con un ADR-F | Baja | ABIERTA |
| G-07 | **Sesión en el navegador sin cookies.** La API entrega el token de acceso y el refresh token en el cuerpo, sin cookies, a propósito (base-shop ADR-0023) | Guardar el refresh token en el navegador lo expone a un XSS. No es una carencia de la API | Se descartó un servidor intermedio con cookie `HttpOnly` por el límite por IP (G-10); la tienda guarda la sesión como el backoffice (ADR-F006). No pide cambios en la API | — | RESUELTA (ADR-F006) |
| G-08 | **Una sola URL de frontend para los correos.** La API arma los enlaces de verificación, recuperación de contraseña y acceso a pedidos con una sola `FRONTEND_BASE_URL` (base-shop ADR-0056), y hoy apunta al backoffice por decisión del usuario (backoffice G-01 y D-032) | Los correos de los clientes llevarían al backoffice, que no tiene `/verify-email` ni `/order-access` para clientes. En local se puede apuntar la variable a la tienda, pero entonces el staff pierde su recuperación de contraseña | Pedida a base-shop el 2026-10-26. Una URL por frontend en la API: `FRONTEND_BASE_URL` para la tienda y otra para el backoffice. La verificación de email y el acceso a pedidos de invitado son solo de clientes y van a la tienda; la recuperación de contraseña elige la URL según el tipo de cuenta. Es un cambio de código en la API que no depende del hosting (el hosting solo fija los valores); el backoffice ya lo dejó previsto en su D-032 | Alta: bloquea verificación de email y recuperación en la tienda | RESUELTA en base-shop 1.8.0 (ADR-0169, T-125): `FRONTEND_BASE_URL` es la tienda (`http://localhost:3002` por defecto) y `BACKOFFICE_BASE_URL` el backoffice; la verificación y el acceso a pedidos van a la tienda, y la recuperación según el tipo de cuenta |
| G-09 | **Una renovación de sesión perdida revoca la sesión.** Si la pestaña se recarga o se cierra después de enviar `POST /v1/auth/refresh` y antes de recibir la respuesta, la API ya rotó el token y el siguiente intento cuenta como reutilización (base-shop ADR-0023). El backoffice lo reprodujo contra la API real (su G-18) | El cliente vuelve a iniciar sesión sin perder datos; el carrito del cliente sigue en la API. Sin solución posible en el frontend | Que la API acepte durante unos segundos el refresh token recién rotado y responda con el mismo par nuevo (la misma propuesta del backoffice) | Baja | ABIERTA |
| G-10 | **Límite por IP sin excepción para un servidor del frontend.** La API limita 100 solicitudes por minuto por IP y no confía en `X-Forwarded-For` mientras no haya hosting (base-shop ADR-0065, ADR-0154, P-06) | No afecta a la SPA (cada cliente usa su IP). Impide renderizar el catálogo en servidor (el modo híbrido guardado en ADR-F005), porque todas las visitas saldrían de la IP del servidor | Al decidir el hosting: que la API confíe en el proxy y en la IP del servidor de la tienda, o que tenga un límite propio para él | Baja hasta salir a producción | ABIERTA |
| G-11 | **Instrucciones de pago solo con el carrito de origen.** Iniciar el pago de una orden de invitado exige el `cartId` de su carrito de origen (base-shop ADR-0063), y la consulta de invitado (`POST /v1/orders/lookup`) devuelve el estado del pago, pero no su `action` con las instrucciones | Si el invitado cierra la pestaña antes de que la tienda inicie el pago, o vuelve desde otro dispositivo, la tienda ya no puede mostrarle las instrucciones de la API; solo el código, el total y el vencimiento. El correo "Orden recibida" sí las lleva | Que la consulta de invitado incluya la acción de pago vigente, o que iniciar el pago acepte el par email–código como prueba, igual que la consulta | Baja: el correo cubre el caso | ABIERTA |
| G-12 | **Límite de `brand` distinto en el OpenAPI.** `openapi/v1.json` declara `maxLength: 100` para todo el parámetro `brand` de `GET /v1/catalog/products`, pero la API valida hasta 20 slugs de 1 a 100 caracteres cada uno (`API_SPEC.md` §11.2, `catalog.dto.ts` de base-shop 1.8.0) | Ninguno hoy: la tienda sigue a `API_SPEC.md` y limita a 20 marcas. Un cliente generado que valide con el OpenAPI rechazaría selecciones válidas | Corregir el decorador en la API para que el OpenAPI diga "hasta 20 elementos" y no 100 caracteres | Baja | ABIERTA |

## Configuración, no brechas

No piden cambios en la API, solo configurarla para el frontend en local:

- `CORS_ALLOWED_ORIGINS` con el origen del frontend, `http://localhost:3002` en local (base-shop ADR-0085, ADR-F010).
- `FRONTEND_BASE_URL` con la URL de la tienda, `http://localhost:3002` por defecto desde base-shop 1.8.0 (G-08), y las páginas `/verify-email`, `/reset-password` y `/order-access` en el frontend (base-shop ADR-0056, ADR-0117, ADR-0118, ADR-0148).
- `IMAGE_BASE_URL` para que las URLs de las imágenes apunten a la API local (base-shop ADR-0121).
